# Rivertown Lead Intake: SQLite schema and integrity tests

Applied evidence for Gate 1 #7 (SQL and state). Built and run 2026-10-15 on Josh's PC with the SQLite command-line tool, version 3.53.4 (installed with `winget install SQLite.SQLite`).

## Files

| File | What it does |
|---|---|
| `schema.sql` | Creates 5 tables: Source, Company, Lead, WorkflowRun, ReviewDecision |
| `seed.sql` | Starter rows: 2 sources (website_form, event_form), 1 company, 1 lead (Dana, FORM-10231 from source 1) |
| `test-duplicate.sql` | Duplicate test for `UNIQUE (external_id, source_id)` |
| `test-invalid-reference.sql` | Invalid-reference test for `Lead.source_id REFERENCES Source (source_id)` |

`rivertown.db` is generated by these files and is not committed. To rebuild from nothing, run from this folder:

    sqlite3 rivertown.db ".read schema.sql" ".read seed.sql" ".read test-duplicate.sql" ".read test-invalid-reference.sql"

## Design in plain words

- **Lead** is the center. Each lead points to the **Source** (form) it came from (required) and optionally to a **Company**.
- **WorkflowRun** records each time the workflow ran (`execution_id` is unique). Its `lead_id` is optional because a rejected submission (400) has no lead.
- **ReviewDecision** records a person's routing decision; its `lead_id` is required.
- `lead_id` is the automatic row number (primary key). It cannot catch duplicates, because every row gets a fresh number.
- `UNIQUE (external_id, source_id)` is the duplicate blocker: the same form number from the same form is a resend. The same number from a different form is a different lead.
- SQLite ignores foreign keys unless each connection runs `PRAGMA foreign_keys = ON;`, so every file starts with it.
- No `ON DELETE CASCADE`: deleting a lead that has runs or review decisions is refused, which keeps the audit trail.

## Test 1: duplicate (2026-10-15) - PASS

Rules written and approved before the run:
1. A (Dana resends FORM-10231 from source 1) is rejected with `UNIQUE constraint failed: Lead.external_id, Lead.source_id`.
2. B (Pat sends FORM-10231 from source 2) is accepted with no error.
3. The Lead table ends with exactly 2 rows: Dana (source 1) and Pat (source 2).

Output:

    === A: Dana resends FORM-10231 from source 1 (website_form). Expect: REJECTED ===
    Error near line 6 of test-duplicate.sql: UNIQUE constraint failed: Lead.external_id, Lead.source_id

    === B: Pat sends FORM-10231 from source 2 (event_form). Expect: ACCEPTED ===

    === Lead table after the test. Expect: 2 rows, one per (external_id, source_id) pair ===
    lead_id | source_id | external_id | email
    1       | 1         | FORM-10231  | dana.okonkwo@meridian-partners.com
    2       | 2         | FORM-10231  | pat.lee@northfield.org

All three rules met.

## Test 2: invalid reference (2026-10-15) - PASS

Rules written and approved before the run:
1. Foreign-key enforcing is on (check line shows 1).
2. Sam's lead, with `source_id` 9 (no such Source row), is rejected with `FOREIGN KEY constraint failed`.
3. The Lead table still has exactly 2 rows: Dana and Pat.

Output:

    === C: a lead claims it came from source 9, which does not exist. Expect: REJECTED ===
    Error near line 10 of test-invalid-reference.sql: FOREIGN KEY constraint failed

    === Lead table after the test. Expect: still 2 rows (Dana and Pat) ===
    lead_id | source_id | external_id | email
    1       | 1         | FORM-10231  | dana.okonkwo@meridian-partners.com
    2       | 2         | FORM-10231  | pat.lee@northfield.org

All three rules met. Rule 1 is shown by the rejection itself: with enforcing off, SQLite would have saved the row.

## Known gap (not fixed here)

The UNIQUE rule cannot tell a resend (same number, same person) from a broken form that reuses a number for a different person. Both are blocked. Handling that belongs in the workflow (threat-model F2), not the schema.

## What is client-specific

Only the seed rows (source names, company, people). The schema and both tests apply to any client whose leads come from one or more numbered forms.
